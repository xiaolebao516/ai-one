## 1.1 开发原则（用户 2026-10-23 追加）

1. **先快速可用，再好看简洁**：功能先跑通；界面精修、精简由 Opus 之后另开 Task，不在本轮追求。
2. **视觉只守一条基线**（§2.1：字体与留白），其余沿用现有 v2 组件，不做新视觉探索。
3. 觉得复杂时按这个顺序保，**开发优先级与 §11 合并顺序完全一致**：L0 视觉基线 → L1 ∥ L2 ∥ L6 → L5 → L3 → L7（含本地任务模型）→ L4 发起任务。L8 额度 HUD、L9 Chat 主导（#113，用户要求尽快跑通）独立并行。“可提前准备”指可以先用演示数据做界面，“必须等待”指真实集成要等依赖合并。

## 2. 共用约定（所有新页面遵守）

沿用 v2-product-design.md §6–§9 与 #79 已实现的外壳；下列是新页面必须守的点：

1. **视觉基线**见 §2.1，所有新页面必须遵守。
2. **组件与令牌**只用 `src/ui/v2`（Badge、Button、Card、SectionHeader、SegmentedControl、Select、Tabs、Notice、States、DispatchReceipts 等）和 `tokens.ts`；不引入新色。缺组件时先在 `src/ui/v2` 补并进画廊，再在页面用。
3. **文案**走 `src/workbench/workbenchText.ts` 的双语表（zh-CN / en），不写死中文。
4. **数据来源标清**：演示 / GitHub 回读 / 本机偏好 / 读不到。读不到就写读不到，不显示旧数据冒充当前（同 #98）。
5. **不用模态框**处理运行中的事；需要你的事是内嵌卡片。写入类按钮**不加额外审批步骤**（沿用 AGENTS.md「不新增工作台自己的写操作审批层」）：按钮本身就是用户的动作，按钮旁只读显示将发出的文字，写后回读，失败可见（§6.3）。
6. **不替用户选**：没有默认选中的决策。
7. **断点**：≥1320 / 1100–1320 / <1100 按 v2-product-design.md §9；最小 1024×720。每个新页面在 1024、1440、1920 与深浅主题各验一遍。
8. **没有无动作的假按钮**：做不到的按钮不显示，或显示为不可用并写明原因。
9. 键盘：可聚焦、焦点环可见、Esc 关浮层；沿用现有 `roving` 方案。

### 2.1 视觉基线（L0 交付，最先合并）

目标：字体和留白看起来高级、安静，不堆边框。只改令牌和共享组件的间距与字体，**不改任何页面的结构和行为**。

**字体**
- 衬线（Claude 风格）只用在“读的东西”：页面大标题、任务标题、任务现场的「现在」一句话、讨论汇总卡的结论、AI 回复正文（对比卡片展开、抽屉里的审计原文）。
- 无衬线用在“操作的东西”：按钮、标签、列表、表单、元信息、侧栏、状态岛。
- 字体栈：
  - 衬线 `--v2-font-serif`：`"Source Serif 4", ui-serif, "Iowan Old Style", "Palatino Linotype", Georgia, "Microsoft YaHei UI", serif`。**随应用打包 Source Serif 4 的 woff2**（OFL 许可，需把许可文本放进仓库）；不依赖在线字体，离线也一致。
  - **中文不回退到宋体**（Windows 的 SimSun 小字号很难看）：衬线栈里中文直接落到 `Microsoft YaHei UI`。所以衬线主要承担拉丁字母和数字的气质，中文标题保持无衬线，这是已知取舍，不做额外处理。
  - 无衬线 `--v2-font-sans` 与现有一致（Segoe UI Variable + 微软雅黑 UI）；等宽 Cascadia Code。
- 字号：页面标题 28 / 任务标题 20 / 正文 14 / 衬线正文（AI 回复）16、行高 1.7 / 元信息 12。数字一律等宽。
- 衬线正文单行最长约 68 个字符（`max-width: 68ch`）。

**留白**
- 基础单位 4px。页面外边距 40（≥1320）/ 28（1100–1320）/ 20（<1100）；区块之间 40；卡片内边距 20–24；卡片内元素间距 12–16。
- **少用边框**：区块之间靠留白和浅底（`sunken`）分隔；一个卡片最多一层发丝线；列表行用行间留白，不画每行边框。阴影只给浮层。
- 标题与正文之间留足行距：标题行高 1.3，正文 1.6。
- 保持现有色彩令牌（暖灰纸面 + 墨色）与状态色，不新增颜色。

**验收**：令牌里新增上述字体、字号、间距变量；`src/ui/v2` 共享组件和 `src/workbench/` 现有页面（总览、任务、任务现场）套用后在 1024/1440/1920 与深浅主题不破版；字体文件与许可进仓库；截图（前后对比）进 PR。

## 3. S1 发起任务（总览输入框）

**位置**：总览页顶部，替换现有“开始”灰按钮的占位逻辑。组件入口 `src/workbench/views/HomeView.tsx` 的 composer。

### 3.1 共同结构

```
┌ 输入框：描述要做的事…（多行，Ctrl+Enter 提交）──────────────┐
│ [聊天] [想需求 /grill] [交给 CC] [流程]      [仓库 ▾] [主按钮] │
│ ── 模式说明区（随模式变化，见下） ───────────────────────────  │
└──────────────────────────────────────────────────────────┘
```

- 四个选项是 `SegmentedControl`；输入框里以 `/` 开头可直接选：`/chat`、`/grill`、`/lead`（交给 CC）、`/flow`，以及内置阶段命令 `/plan`、`/split`、`/build`、`/ship`。输入 `/grill 需求文字` 自动切到想需求并把后面的文字当正文。**阶段命令的独立触发**（Spec #32 允许跳过阶段、直接执行某一阶段）：`/plan`、`/split`、`/build`、`/ship` 走“交给 CC”路径，Issue 正文的「任务与范围」里写“只做这一个阶段：<阶段定义>，不要执行其他阶段”，CC 只执行该阶段；`/grill` 仍由 ai-one 内置讨论引擎直接运行；聊天页只支持 `/grill`，其余阶段命令只在总览输入框可用。解析是纯函数，放 `src/workbench/composerModel.ts`，要有单元测试。
- 选了仓库时默认“交给 CC”；没选仓库默认“聊天”。
- 仓库下拉的候选来自 GitHub 数据源里已读到的仓库；没有候选时只显示“手动输入 owner/repo”。
- 主按钮文案随模式：`发送` / `开始讨论` / `交给 CC` / `开始流程`。输入为空时按钮不可用并提示“先写要做的事”。
- 提交后按钮进入“处理中”，**完成前不重复提交**；失败显示行内错误，保留输入内容。

### 3.2 聊天

- 说明区：`发给` + 各 AI 的 chip（ChatGPT、Claude、Gemini、Grok；默认选中：上次发送成功过且当前不是“未登录”的；`未登录` 虚线、不可选；`未探测` 可手动选，标“未探测”）。
- 点发送：把消息发给选中的 AI，**跳到聊天页**（S2）的对比视图，新建一个对话。
- 复用旧界面的发送能力（`src/workflow/`、`src/host`），不重写发送逻辑 [待核实：发送入口是否可脱离旧 `App.tsx` 单独调用，实施时先确认并在 PR 说明]。
- 全部都是“未登录”时按钮不可用，说明区写“没有可用的 AI，先到资源页或聊天页登录”；有“未探测”的不算不可用。

### 3.3 想需求 /grill

- 说明区：`团队` chip 行（讨论者两位、可选审计者一位，默认值来自 #18 引擎的默认角色分配 `src/ui/modeRoleAssignment.ts`）+ 预检行。
- 预检行：有人没登录时，直接给「打开网页登录」「本次用 XX 代替」两个操作，**不静默换人，不弹窗**。复用 `src/ui/preflightModel.ts`。
- 点开始：在 ai-one 内**直接跑讨论引擎**（#18），不经 CC。创建一个“讨论任务”（无仓库、单阶段），跳到任务现场，现场显示讨论矩阵（S5）。
- 说明区下方固定小字：“独立作答 → 交换完整回复 → 汇总。AI 同意不等于事实已验证。”

### 3.4 交给 CC

- 说明区：`CC 协调` 标记 + 一行“经 Prodex 派 GPT 执行/审计，需要时请 Argon、Opus”。
- 说明区第二行写清楚后果：“点‘交给 CC’后，ai-one 会建一个 Task Issue，并把接手指令放进剪贴板，你粘贴给 Claude Code。”
- 点「交给 CC」后的步骤（行内进度，不弹窗）：
  1. 建 Task Issue。正文**按 `.github/ISSUE_TEMPLATE/task.md` 生成**，字段如下：`关联 / 派工`（Parent Spec：用户选了才填，否则“无”；**写入桥不建立 GitHub 原生 Sub-issue 关系**，正文写明“原生子 Issue 关系待 CC 接手时建立（工具不能建时报告待关联，不伪报完成）”；Reviewed Spec Revision：随父 Spec；Complexity：默认 `ROUTINE`；Owner：“待 CC 接手后登记”；Reviewer：“ChatGPT（独立审计，经 Prodex 新对话）”；Depends on：无）、`任务与范围`（**需求原文原样放这里**；非目标：“由 CC 与用户确认后补”）、`交付 / 验收标准`（写“**验收标准待 CC 在开工前补齐，补齐前不得开始实现**”并留空勾选项）、`实施与验证记录`（PR：待创建），末尾附「协调简报」（S6）与来源“由 ai-one 创建”；
  2. **回读** Issue 确认已创建（拿到编号和链接）；
  3. 复制接手指令：`按 AGENTS.md 快速开发模式接手 <owner/repo> 的 Issue #<N>`；
  4. 显示结果卡：`已创建 #N · 接手指令已复制` + 「在 GitHub 打开」「再复制一次」「查看任务」。
- 任何一步失败：显示是哪一步失败、原因（不回显 gh stderr）、能做什么（重试 / 手动建）；**回读不到时不重试建单**，先让用户确认（避免重复建 Issue，遵守 AGENTS.md“结果不确定先回读”）。
- 依赖：GitHub 写入桥的 `create_issue` 动作（§6.3）。

### 3.5 流程

- 说明区：`流程 [快速开发 ▾]` + 阶段缩略（`定方案 → 执行与审计 → 总结`）+ `本次参与者` chip + `临时调整`。
- 下拉里每项：流程名 + 一行说明 + 「查看阶段」（展开该流程的阶段卡片，只读）。数据来自 S3 保存的流程。
- 「临时调整」：展开本次的参与者与角色编辑（同 S3 阶段编辑面板的子集），**不改保存的流程**，只写进这次 Task Issue 的协调简报。
- 点「开始流程」：同 §3.4，建 Task Issue，正文里额外带“流程定义”（流程名 + 每个阶段的协作方式、参与者、结束条件、失败时），CC 照它推进。
- 没有可用流程时，下拉只有「去阶段与流程页新建」。

### 3.6 测试与验收要点

- `composerModel`：斜杠解析、模式默认值、按钮可用性、提交状态机（空 / 处理中 / 失败 / 成功）有单元测试。
- 失败路径有测试：建单成功回读失败；回读成功复制失败（Tauri 剪贴板不可用时，结果卡里显示可手动复制的文本框）。
- 真机：Windows Tauri 里完成一次“交给 CC”（对用户自己的测试仓库），截图进 PR；剪贴板内容可核对。

## 4. S2 聊天页

**位置**：侧栏「聊天」。替换 `PlannedView`。

### 4.1 布局

```
┌ 对话列表 180 ─┬ 顶部标签：[对比] [ChatGPT] [Claude] [Gemini·未登录]…   [转为任务…] [⋯] ┐
│ ＋ 新对话      │ 你：<本轮问题>                                                       │
│ 对话 A (选中)  │ ┌ ChatGPT ┐ ┌ Claude ┐ ┌ Gemini ┐   ← 对比卡片，按列并排，窄则换行   │
│ 对话 B         │ │ 状态+摘要│ │ …      │ │ 未发送  │                                    │
│ …              │ │ 展开 转发 引用 在网页中查看 │                                        │
│                │ └─────────┘ └────────┘ └────────┘                                    │
│                │ 底部：[继续问…]  [目标 chip…] [模式 ▾] [附件] [发送]                  │
└───────────────┴──────────────────────────────────────────────────────────────────┘
```

- 对话列表 <1100 宽时收起，只在标题区留一个“对话”按钮展开。
- 标签：`对比` 是默认；其他每个标签是该 AI 的**真实网页**（登录、手动操作都在这里）。未登录的 AI 标签显示“未登录”，点开是登录页。
- **网页窗口与外壳（现状与本页要补的）**：[已核实] 当前 `Workbench` 调用 `useHideProviderWebviews()`，把所有原生 WebView 隐藏；`FocusPane` 的 bounds 管理与 `useOverlayGuard` 尚未接入工作台。原生 WebView 画在 DOM 之上，**不能靠 CSS 保证不盖外壳**。本页（L6）必须新做：
  - 把 WebView 的 bounds 同步到网页标签内容区的 DOM 矩形（ResizeObserver + 窗口 resize / DPI 变化 + 主区滚动时更新）；
  - 以下任一情况出现就**隐藏** WebView，关闭后恢复：命令面板、检查器抽屉、对话列表浮层、通知条之上的任何浮层、切到非网页标签或别的页面、窗口最小化；焦点从网页回到外壳时键盘快捷键仍可用；
  - “网页标签不遮挡外壳”列为真机验收项（侧栏、标题栏、命令面板、抽屉各截一张）。
- **登录状态的数据来源**：[已核实] 工作台目前**没有**读取各 AI 登录状态的能力（只在旧界面打开网页时检查）。本稿所有“已登录 / 未登录”显示统一为三态：`已登录`、`未登录`、`未探测`。数据来源复用旧界面的探测（`providerChipState` 与适配器的登录检测），由 L6 接入工作台；没探测过就是“未探测”，**不当作未登录，也不默认选中**，但允许用户手动选，发送时按真实结果报告。

### 4.2 对比卡片

每个目标 AI 一张卡，状态五种：`已完成`、`生成中（计时）`、`未发送（未登录/未选中）`、`失败`、`已超时`。

- 卡内容：AI 名与档位标签、状态、回复摘要（前约 4 行，**不改写原文**，只截断）、操作行。
- 操作：
  - **展开**：卡片原地展开为完整回复（Markdown 渲染，复用 `MarkdownText`）；
  - **转发给…**：见 §4.3；
  - **引用**：把这段回复（或选中的片段）作为引用块插进底部输入框；
  - **在网页中查看**：切到该 AI 的网页标签并滚到对应回复 [待实测：能否定位到具体回复；不能则只切标签，并在 PR 说明]。
- 生成中的卡片只显示“生成中 12s”和已有内容，不显示“即将完成”这类没有依据的话。
- 失败/超时卡片给「重试」「跳过」，沿用 `StepTimeoutDialog` 的语义，但以内嵌卡片呈现。

### 4.3 转发与引用（新功能）

- 点卡片「转发给…」→ 行内出现目标 AI 选择（chip，排除自己和未登录的）+ 一个可选的“附言”输入框 + 「发送」。
- 发送内容 = **完整原文**（不是摘要）+ 附言；消息里注明来源 AI 名，格式沿用讨论引擎已有的“交换完整回复”模板（`src/workflow/graph/deliberation*` 的 relay 文案），不另造模板。
- 转发的结果出现在目标 AI 的卡片里，卡片上标“收到转发自 XX”。
- 同一个 AI 有进行中的发送时，转发按钮不可用并写“XX 正在回复”（沿用 #15 忙碌门禁）。
- 引用只改输入框内容，不发送。

### 4.4 底部输入区

- 目标 chip 多选（默认选中上次发送成功的组合；`未登录` 虚线不可选；`未探测` 可手动选）。
- 模式下拉只有 4 项：`自由`（默认）、`辩论`、`咨询`、`双 AI 讨论`。其中**双 AI 讨论**不在聊天页内运行：选中后输入区提示“将在任务里运行”，点发送等同于 S1 的 `/grill`（跳任务现场）。理由见 D3。
- 附件：沿用 `fileAttachments`、`fileDrop`（只读复用）。
- 快捷键：Enter 发送、Shift+Enter 换行（沿用旧界面习惯）。

### 4.5 转为任务

- 顶部「转为任务…」：带上当前对话的最后一个问题和（可选）全部对比摘要，回到总览输入框并预填，模式默认“想需求”。不自动提交。
- 「⋯」菜单：回放（`ReplayPanel`）、导出 Markdown（`exportMarkdown`）、重命名、删除对话（行内提示一次，只删本地对话记录，不碰 AI 网页里的会话）。

### 4.6 数据与复用

- 复用：`src/ui/conversationSessions.ts`、`ConversationSidebar` 的会话数据、`TargetChips`、`MarkdownText`、旧界面的网页窗口宿主（`FocusPane` 的窗口管理能力）。新代码放 `src/workbench/views/chat/`。
- 不改旧界面行为；需要抽取共用逻辑时做最小改动并在 PR 说明。

### 4.7 测试与验收要点

- 卡片状态派生（五种）、转发消息构造、引用插入、预设下拉内容有单元测试。
- 多 AI 同时发送、一个失败不影响其他的场景有测试。
- 真机：至少两个真实 AI 登录后，完成“发送 → 对比 → 转发 → 引用 → 转为任务”一遍，截图进 PR；网页标签不遮挡外壳。

## 5. S3 阶段与流程页（可编辑）

**位置**：侧栏「阶段与流程」。替换 `PlannedView`。

### 5.1 概念（写进页面顶部一行说明）

- **阶段** = 一个完整的工作环节：谁参与、怎么配合、怎么算结束、失败了怎么办。
- **流程** = 把几个阶段按顺序排起来。
- 页面顶部说明一句话：“阶段是一个工作环节，流程是把几个阶段排成顺序。你可以自己建、改、保存。”

### 5.2 布局

三栏（≥1320）：左 170 列表 | 中 流程卡片 | 右 阶段编辑面板。1100–1320：右栏改为选中阶段时滑出的面板。<1100：左列表收成下拉。

```
左：＋新建流程 / 我的流程（列表）/ ＋新建阶段 / 阶段库（列表）/ CC 协调设置
中：流程名 [复制][保存]
    1 定方案        ⋮⋮ 拖动排序
    ＋ 在这里插入阶段
    2 执行与审计 ← 选中
    ＋ 在这里插入阶段
    3 总结交付
    ＋ 添加阶段（从阶段库选，或新建）
右：编辑阶段：协作方式 / 参与者与角色 / 思考深度 / 怎么算结束 / 失败时 / [另存为新阶段] [从流程移除]
```

### 5.3 数据模型（纯类型 + 校验，放 `src/stages/flowModel.ts`）

```ts
type Collaboration = 'solo' | 'discussion' | 'author-review' | 'parallel';
interface Participant { resource: string; role: string; model?: string; effort?: 'default' | 'high' | 'max'; freshSession?: boolean }
interface StageDef {
  id: string; name: string; command?: string;      // 如 'grill'，对应 /grill
  collaboration: Collaboration;
  participants: Participant[];
  note?: string;                                    // “补充说明”（可选，写给 CC；持久化，并渲染进 Issue 的流程定义）
  endCondition: EndCondition;                       // 枚举：user-confirms | audit-pass | audit-pass-and-local-verify | rounds-done | all-subtasks-done
  onFail: FailPolicy;                               // 枚举：stop-and-ask | retry-n | skip | escalate-to-user
  reworkLimit?: number;                             // 主写+审计用，默认 3
  builtin: boolean;                                 // 内置阶段不可删，可“复制后编辑”
}
interface FlowDef { id: string; name: string; description?: string; stages: StageRef[]; builtin: boolean }
interface StageRef { stageId: string; overrides?: Partial<Pick<StageDef,'participants'|'endCondition'|'onFail'|'reworkLimit'|'note'>>; /* 预留 */ next?: never }
```

- `next?: never` 是**分支预留位**：本期永远不出现，但文件格式 `schemaVersion: 1` 留好，以后加分支不破坏旧文件。
- 校验规则（有测试）：流程至少 1 个阶段；协作方式与参与者数量/角色匹配（`author-review` 至少一个作者一个审计且**不是同一会话**；`discussion` 至少两位）；返工上限为 1–10 的整数；引用的阶段必须存在。
- **固定安全规则不可编辑**（页面里作为只读提示展示，不是选项）：作者不审自己；审计针对当前完整 HEAD；合并只由用户或 Issue 登记的调度 agent 在审计 PASS 后做；Prodex 结果不明先恢复不重发。编辑器里不提供关闭它们的开关。

### 5.4 内置内容（首次启动写入，标 `内置`）

| 类型 | 内置项 |
|---|---|
| 阶段 | 想需求 `/grill`、定方案 `/plan`、拆任务 `/split`、执行与审计 `/build`、总结交付 `/ship` |
| 流程 | 快速开发（定方案→执行与审计→总结交付）；CC 设计·并行开发（定方案→拆任务→执行与审计[并行]→总结交付）；只讨论需求（想需求） |

内置项的定义与 v2-product-design.md §2、§4C、原型 10 一致。内置项**可复制后编辑，不可直接改、不可删**；复制出的叫“<原名> 副本”。

### 5.5 交互

- **新建流程**：输入名称 → 空流程 → 「添加阶段」从阶段库选或新建。
- **添加 / 插入阶段**：弹出行内选择列表（阶段库），选中即加入；或「新建阶段」进入右侧编辑面板。
- **拖动排序**：卡片左侧把手，键盘上 Alt+↑/↓ 等价（无障碍）。
- **编辑阶段**：右侧面板改的是**阶段库里的那份**。若该阶段被多个流程引用，保存前行内提示“这会同时改变 N 个流程”，并给「只改这个流程」（写入 `overrides`）与「改阶段库里的」两个按钮，不默认选。
- **保存**：校验通过才可保存；失败逐条列出原因，定位到出问题的阶段卡片。有未保存修改时离开页面，行内提示（不弹模态）。
- **复制 / 删除**：删除自建流程或阶段是本机数据操作，删除前行内提示一次（本地数据确认，不属于 GitHub 写入审批）；被流程引用的阶段不可删，提示引用它的流程名。
- **导出 / 导入**：「⋯」菜单里“导出为文件…”（单个流程 + 它依赖的阶段，JSON）、“导入文件…”。导入时先校验、显示将新增/覆盖的项，**同名冲突时让用户选“保留两者（重命名）/ 覆盖 / 取消”**，不静默覆盖；`schemaVersion` 不认识时拒绝并说明。

### 5.6 存储

- 位置：ai-one 本机数据目录下的 `flows.json`（单文件，含 `schemaVersion`、`stages`、`flows`）。[已核实] 当前 `src/host` **没有**通用文件读写 API，所以实施必须新增**受限 Tauri 命令**：命令只接受**固定文件名枚举**（`flows` | `coordination` | `localTasks`），**不接受前端传入任意路径**；本稿涉及的三个文件共用这一组命令（L2 先建，L3/L7 复用）。
- 写入用“先写临时文件再原子替换”。**并发保证（如实）**：原子替换只保证单次替换不写坏文件，**不防并发丢更新**；本期语义是 last-write-wins + 每次覆盖前保留上一版备份（`<name>.bak`），不做锁或合并，页面「⋯」里写明。
- 读到损坏的文件时**不覆盖**，备份为 `<name>.bak-<时间>` 并提示用户，再回退到内置项。

### 5.7 与运行的关系（诚实边界）

- 流程目前**由 CC 推进**（D8）：开始流程时，流程定义被写进 Task Issue 的“流程定义”段落，CC 读它推进。**ai-one 不会自己按流程自动派工**；这一点写在页面「怎么运行」的一行说明里。
- 因此编辑器里的“怎么算结束 / 失败时”是**写给 CC 的约定**，不是程序强制执行的状态机。页面上这两项标题旁标“CC 参照执行”。以后做成程序自动循环时再改成“程序执行”（需要新 Spec，对应 v2-product-design.md §10 第 7 步）。
- 「想需求」阶段例外：它由 ai-one 内置讨论引擎直接运行（S1 §3.3 / S5）。

### 5.8 测试与验收要点

- `flowModel` 校验、阶段引用与 `overrides` 解析、导入冲突处理、`schemaVersion` 拒绝有单元测试；存储的原子写与损坏恢复有测试（可注入文件接口）。
- 页面：新建流程→加阶段→拖动→保存→重启仍在；复制内置后编辑；导出再导入。1024 宽与深浅主题不破版；键盘可完成排序。
- 真机：Windows 上真实读写本机文件，截图进 PR。

## 6. S4 任务现场补全

在 `src/workbench/views/TaskView.tsx` 基础上增加。已有部分（面包屑、阶段条、「现在」、「需要你」、证据、交付栏）**不改行为**。

### 6.1 检查器抽屉

- 入口：事件行末尾的小链接——`派工单 ›`、`原始输出 ›`、`审计原文 ›`、`Diff ›`；以及右栏「检查器」按钮。点击在**主区右侧滑出抽屉**（≥1320 占 380 宽并把主区挤窄；<1320 覆盖在主区上并带遮罩，Esc 关闭）。
- 抽屉标签：`派工单` · `原始回复` · `Diff` · `测试`。
  - **派工单**：该次派工的 Prodex 回执**元数据**（request_id、状态、槽位、时间；对话地址默认折叠）。数据来自 #80 的 `host.dispatch.snapshot`，复用 `DispatchReceipts` 组件。[已核实] 该接口只含元数据，**不含首条派工消息或回复正文**（#80 范围即只读元数据），所以本页**不显示派工消息正文**；若以后要显示，需另立 Spec 定义受限数据来源与隐私边界。
  - **原始回复**：这一标签只显示“已回读到的 GitHub 内容”（审计评论原文、PR 描述），并写明“不含 AI 网页对话正文”。任务检查器**不读取网页对话正文**（见 §9 的隐私边界区分）。
  - **Diff**：链到 GitHub 的 PR Files 页（`在 GitHub 打开`），不在 ai-one 内渲染 Diff（本期）。显示 PR 编号、完整 HEAD、变更文件数（来自已有 GitHub 回读）。
  - **测试**：CI 状态（已回读）+ 事件里记录的“CC 本机运行”结果；无记录写“未运行”。
- 抽屉里每条信息标证据类型（已回读 / CC 本机运行 / xx 自述 / 未运行），沿用 `EVIDENCE_TONE`。
- 抽屉是只读的；不提供编辑、重发、恢复。

### 6.2 接管入口

- 位置：右栏「团队」里每个参与者行的「接管」。
- 行为：切到该 AI 的真实网页视图（同聊天页的网页标签），顶部固定一条提示条：“你正在自己操作 XX 的网页。ai-one 不会读取网页内容。”和「回到任务」。
- **不做**“交还时采用网页里最新回复”（原型 13 的功能）：ai-one 不指挥 CC，也不读网页正文，做不到就不放。需要让 CC 知道时，用「给 CC 留言」。
- 本地 Agent（CC、Codex）没有网页：这些行不显示「接管」。

### 6.3 GitHub 写入桥（五个固定动作）

放行范围，**只有这五个动作**。Rust 侧命令枚举与参数形状固定如下（前端不能传任意路径、方法或额外字段）：

| 动作（命令名） | 参数 | GitHub 操作 | 前端入口 |
|---|---|---|---|
| `create_issue` | `repo`、`title`、`body` | 在用户指定的仓库建一个新 Issue（不加标签） | 总览「交给 CC」「开始流程」；汇总卡「转入定方案」 |
| `comment` | `repo`、`issue`、`text` | 在指定 Issue 上发一条评论 | 「给 CC 留言」 |
| `set_pause` | `repo`、`issue`、`state: "paused" \| "running"` | 发评论，正文格式见下方「评论统一格式」；中间一行：paused=“用户已暂停：请停止派发新工作，正在进行的一步可完成。” / running=“用户已恢复：可继续派发。” | 「暂停」「继续」 |
| `accept` | `repo`、`issue`、`pr`、`expectedHead`（40 位 SHA） | **先重新读取该 PR 当前 HEAD，与 `expectedHead` 不一致就拒绝，不写任何东西**；一致才：①发评论“【ai-one】用户验收通过（针对 HEAD <SHA>）。” ②移除 `needs-user` 标签 | 「验收通过」 |
| `request_changes` | `repo`、`issue`、`pr`、`expectedHead`、`text`（必填） | 同样先校验 HEAD；①发评论（用户意见 + HEAD）②加 `needs-review` 标签 | 「要求修改…」 |

（“暂停/继续”是同一个动作 `set_pause` 的两个取值，所以仍是**五个动作**，测试按这五个命令名与上表参数形状实现。）

约束：

- **评论统一格式**（所有写评论的动作一致）：第 1 行固定前缀 `【ai-one 代用户发出】`；第 2 行起是该动作的固定模板句或用户自由输入（原样附上，不改写；`accept` / `request_changes` 含完整 HEAD）；最后一行隐藏标记 `<!-- ai-one:<action>:v1 -->`（`<action>` 取 `comment` / `set_pause` / `accept` / `request_changes`）。暂停状态识别只认带该标记的 `set_pause` 评论。
- **不合并、不关单、不删评论、不改已有 Issue 的标题或正文、不改其他标签**（`create_issue` 只创建新 Issue；`pause`/`resume` 只是评论）。
- **写后回读**与结果状态（四态，界面逐个如实显示）：`confirmed`（全部回读确认）、`partial`（复合动作只成功了一步，如评论发出但标签没改成，界面写明哪一步成功、哪一步失败，**不显示成全成功**，不自动重试）、`unconfirmed`（已发出但没能确认）、`failed`。复合动作的顺序固定为先评论后标签。
- **HEAD 防陈旧在桥接端强制**：`accept` / `request_changes` 在写入前由 Rust 端重读 PR HEAD 比较，不依赖界面快照；界面快照不一致时按钮另显示“HEAD 已更新，先刷新”。
- **不加审批层**：点按钮即执行；按钮旁固定显示将发出的评论文字（只读提示，不是确认步骤）；评论发出后不可撤回，界面写明“评论发出后不能撤回”。
- 失败信息不回显 gh stderr（同 #51 约定）；没有 gh 登录时显示“没有可用的 GitHub 登录”，按钮不可用。
- “验收通过”**只表示用户验收，不合并**；界面文案写“验收通过（不会合并）”。**合并口径只有一个：以 `main/AGENTS.md` 快速开发模式为准**——Issue 上登记的调度 agent 在独立审计对当前 HEAD 给 PASS 后自行 squash 合并。`v2-product-design.md` §4B/§7 与 Spec #32 第 6 条里“最后合并由用户确认”的旧表述已被该规则取代，随 Spec #32 升 v2 一并更正（见附）。
- 数据源是“演示数据”时，这些按钮不可用并写“演示数据，不会真的发出”。

### 6.4 底部「给 CC 留言」栏

- 位置：任务现场主区底部，仅当任务有 GitHub Issue 时出现。
- 输入框 + 「留言」按钮。点击即调用 `comment`（你输入并点按钮就是确认）。
- 文案明确：“写成 Issue 评论，注明来自你；CC 下次读到 Issue 时会看到。”不暗示实时送达。
- 留言成功后在事件列表里追加一条“你 · 留言”（来自回读到的评论，不是本地乐观添加）。

### 6.5 暂停与继续

- 顶部状态区「暂停」按钮（任务进行中且有 GitHub Issue 才显示）。点击 → 调用 `set_pause(paused)` 写评论 → **回读确认评论存在后**，状态胶囊旁立即显示 `已暂停`（你下的指令）。
- 暂停状态的判定是确定的：取该 Issue 上带固定前缀与隐藏标记（`<!-- ai-one:set_pause:v1 -->`，格式见 §6.3）的 `set_pause` 评论里**最新的一条**；`paused` 为最新则已暂停，`running` 或没有则未暂停。不解析 CC 或其他人的评论内容，不猜测。**已知限制**：所有 agent 与用户共用同一 GitHub 账号，无法证明某条评论确由 ai-one 写入，前缀与标记只能区分格式，不能防伪造；这一点写进 PR 与用户文档，不宣称防篡改。
- 按钮旁固定小字，如实写限制：“CC 正在执行的这一步会跑完；下一步起读到暂停就停。”不写“已停止”“立即停止”。
- 已暂停时按钮变「继续」→ 调用 `set_pause(running)` 写评论。
- 配套规则（实施时同步写进 AGENTS.md，由该线 PR 一并提出）：**agent 每次派发新工作前先读 Issue，发现最新的 ai-one 暂停/继续评论是暂停就不派发，等继续。**
- 回读失败（评论发出但没能确认）：显示“已发出，但没能确认”，不改状态标记，不自动重试。

### 6.6 验收卡按钮

「需要你：验收」卡片上的按钮（已有「查看验收单」「在 GitHub 打开」）增加：

- **验收通过**：→ `accept`（§6.3，携带卡片读到的完整 HEAD 作为 `expectedHead`）。按钮旁显示完整 HEAD；界面发现 HEAD 已变化时按钮变为“HEAD 已更新，先刷新”，且桥接端仍会再校验一次。
- **要求修改…**：展开多行输入（必填）→ `request_changes`。
- 「决策」卡（`decide`）没有默认选项；本期它只提供「在 GitHub 打开」和「给 CC 留言」，不做“采用方案 A/B”按钮（决策内容格式没有定义，不凭空造）。

### 6.7 通知

- 窗口不在前台且出现新的“需要你”时，发 Windows 系统通知；点通知回到对应任务。窗口在前台时只在右下角显示通知条（深色 island 样式）。
- 通知内容只含任务标题与类型（决策/验收/阻塞），不含正文。
- 本期**不做应用内通知开关**（避免新增设置入口）；要关就在 Windows 系统设置里关 ai-one 的通知。[待实测：Tauri 通知权限与 Windows 勿扰模式表现]

### 6.8 测试与验收要点

- 写入桥：白名单校验、参数校验（编号、HEAD 40 位）、模板文案、写后回读 `confirmed` / `partial` / `unconfirmed` / `failed` 四态有 Rust 与前端测试；确认**拒绝**非白名单动作、非法参数与 HEAD 不一致（用测试证明 HEAD 变化时不会写入）。
- 暂停状态派生（未暂停 / 已暂停 / 标记缺失或格式不对按未暂停）有测试。
- 抽屉各标签空/有数据/读不到三态有测试；证据类型标注正确。
- 真机：对用户自己的测试 Issue 做一遍“留言 → 暂停 → 继续 → 验收通过（HEAD 变化被拦）→ 要求修改”，**回读 GitHub 与界面一致**，截图进 PR。

## 7. S5 讨论接入工作台

- 组件已由 #81 交付（讨论矩阵、汇总卡、`/grill` 解析）。本项做**接入**，并先补一个前置：**本地讨论任务的数据模型**。
- **本地任务模型**：[已核实] 当前 `useWorkbenchData` 的 tasks 只来自演示数据或 GitHub 回读，任务路由只在 `data.tasks` 里找 `HudTask`，所以必须扩展：
  - 记录 `LocalTask`：`id`（`local:<uuid>`）、`kind: 'discussion'`、`title`、`createdAt`、`status`（进行中 / 待你 / 已完成 / 已结束）、`stage: '想需求'`、讨论引擎会话 id、汇总结果、来源对话 id（聊天页“转为任务”时带入，可空）。
  - 持久化：`localTasks.json`（§5.6 的受限命令，固定文件名枚举），带 `schemaVersion`；刷新或重启后恢复；“结束并保存”写入汇总并标记完成。
  - 接入：`WorkbenchData.tasks` = 演示 / GitHub 任务 ∪ 本地任务（本地任务带 `dataSource: 'local'`，任务列表里单独“讨论”分组，不混进仓库分组）；路由 `task/local:<uuid>` 从本地存储取；数据源切换（演示 ↔ GitHub）时本地任务始终显示（它们不属于任何数据源）。
- 「想需求」任务的任务现场：阶段条只有一格“想需求”；主体用讨论矩阵（行=环节：独立思考、第 1 轮、审计、第 2 轮…；列=参与者；每格一句摘要，独立思考阶段两列同时“思考中，看不到对方”）；结束出现汇总卡。样式见原型 05。
- 汇总卡的操作：
  - **转入定方案**：建一个 Task Issue（同 S1 §3.4，正文 = 汇总卡内容，模式预选“交给 CC”），不自动开跑；
  - **继续追问**：回到该讨论追加一轮；
  - **结束并保存**：保存汇总并标记完成。
- 讨论任务没有 GitHub Issue 时：「给 CC 留言」「暂停」等 §6 的写入按钮**不显示**（没有写入目标）。
- **恢复语义**：[UNVERIFIED] 讨论引擎能否从保存状态恢复运行、能否对已完成的讨论追加一轮，须由 L7 开工时先验证并写入 PR；设计上的约定如下（引擎做不到的部分如实标注不可用，不伪装）：
  - 重启或刷新后，**进行中的讨论不自动继续**，任务标记“已中断”，显示已完成环节的摘要与汇总（若已有），提供「重新开始」（新开一次运行，把已保存的前文摘要作为上下文，不复用旧的网页会话）；
  - 已完成的讨论：「继续追问」= 以保存的汇总为上下文新开一轮运行，产物追加到同一个任务的记录里；
  - 引擎不支持时，这两个按钮显示为不可用并写明原因。
- 依赖：L7 先交付本地任务模型与接入；L4 的“想需求”入口依赖 L7（L4 的其余模式不依赖）。

## 9. 诚实边界与明确不做

- ai-one **不直接指挥 CC**，不拉起 CC 进程；一切靠 Issue（D8）。
- 流程的“结束 / 失败时 / 返工上限”是写给 CC 的约定，不是程序强制（§5.7、§8）。
- **隐私边界（区分清楚，不是一刀切）**：
  - 聊天页是对话功能：允许通过既有桥读取并展示、转发 AI 回复，并按既有规则把会话保存在本机（`conversationSessions`）；
  - **不允许**把网页对话正文写进仓库、Issue、PR、GitHub 评论、日志（AGENTS.md「账号与安全」）；
  - 任务现场的检查器与接管：**不读取网页对话正文**；Prodex 元数据与派工回执不承载正文；人工接管不抓取网页内容；
  - 讨论汇总里写入 Issue 的是汇总结论，不是网页对话原文。
- 不做：节点图画布、流程嵌套、程序自动解析 REVISE 并派工、反向派工、CC 终端视图、交还时采用网页回复、Diff 内渲染、额度识别、自动合并。
- 数据源为“演示数据”时，所有写入按钮不可用并说明。
- 「验收通过」不合并；合并口径见 §6.3（只以 AGENTS.md 快速开发模式为准）。
